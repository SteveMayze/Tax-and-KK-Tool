# ADR 0012: One app-wide language (English default, German), language-independent CSV

Status: accepted (Phase 12, 2026-10-19; owner answers: one setting for the whole app; CSV stays comma-separated with dot decimals in every language; CSV headings always English; glossary approved).

## Decisions
1. **One setting.** `AssessmentSettings.language` (`en` default, `de`) is the single source. A small middleware (`core.middleware.LanguageMiddleware`) activates it for every request, so interface text, number formats and date formats follow it. The header has EN / DE buttons (a POST form, no JavaScript); the choice is saved and applies at once. Django's `LocaleMiddleware`, cookies and per-session languages are not used: there is one user and one setting.
2. **Formats are screen/print only.** English shows `1,234.50` and `2026-10-19` (exactly as before). German shows `1.234,50` and `19.10.2026`, via `core/formats/{en,de}/formats.py` and `core.services.i18n`. Amounts keep their own ISO currency code; nothing is converted by the language. Reports stay in EUR. Calculations never use the formatting helpers.
3. **CSV is language-independent.** Delimiter `,`, decimal point, no thousands separator, ISO dates, 2 decimals, **English headings and labels** whatever the interface language is (the CSV is for bulk data input, and exports from either language can be mixed). The import format is the same. Each export says so in `Language` and `Format` rows. Rejected: a German CSV with `;` and decimal comma (mixing files would break), translated CSV headings.
4. **Glossary is the source of the German report terms** (`docs/glossary.md`, approved by the owner on 2026-10-19; the wording is Claude's proposal except where the file marks an SBK-page quote). A test requires every German heading and title on the report pages to appear in the glossary, and the 14 SBK columns to equal the glossary labels.
5. **Translation files.** `core/locale/de/LC_MESSAGES/django.po` is committed with the compiled `django.mo`; a test fails if the `.mo` is stale or any message is empty, fuzzy or has different placeholders. The image build needs nothing extra because `COPY core` ships the `.mo` (this replaces "compile at build time", so the build needs no gettext package). Update: `python manage.py makemessages -l de --no-obsolete --no-location -i ".venv*" -i staticfiles -i local -i docs -i infra -i "core/test_*"`, translate, `msgfmt -c -o core/locale/de/LC_MESSAGES/django.mo core/locale/de/LC_MESSAGES/django.po`.
6. **Falls back to English** (not translated): technical identifiers shown as data (policy version and source names such as "sbk-contribution-estimate 1.0 ...", rate sources like "manual"), notes stored in the database at the time of a conversion (for example "Manually entered rate."), user-entered names (organisations, categories, comments), the seeded English category names, and the provider/HTTP error texts of the exchange-rate service. Import row messages are stored with the row when it is staged, so they stay in the language that was active at upload.

## Consequences
Existing English tests pass unchanged. A German page never needs a restart or a second deployment: the setting is data.
