# ADR 0035: Storage on /u01 and PostgreSQL

Status: **storage part (decisions 1 to 4) accepted: implemented in Phase 36 (PR #7) and carried out on the server in Phase 37 on 2026-11-27. Database part (5 to 12) final as implemented in Phase 38 (branch `feat/u01-postgres`, not deployed); it becomes accepted with the Phase 39 cutover.** Drafted in Phase 35 (2026-11-27, branch `docs/phase-35-design`). Plan: `docs/prompts/PHASES_12.md`. Findings: `docs/u01-postgres-findings.md`. This ADR is accepted in stages. Phase 36/37 accept the storage decisions, and Phase 38/39 accept the database decisions.

## Context
The app runs as the rootless Quadlet container `tax-healthcare-tool-web` of `homeapps` (ADR 0007 to 0009). Its SQLite database, the stored original statements and its backups are in `~/tax-healthcare-tool/{data,uploads,backups}` on the eMMC. On 2026-11-27 these were 1.8 MB, 101 MB (30 files) and 1.8 GB (21 archives), with 15 GB of 27 GB free on the eMMC. A 1 TB disk is mounted at `/u01`. The platform repository runs a shared PostgreSQL 17.11 container `postgres` on the Podman network `db`, with the empty database `taxtool`, the role `taxtool` (not a superuser, `NOCREATEDB`) and the secret `taxtool-db-password`, plus nightly dumps, an offsite copy and disk-health checks (platform ADR 0005, contract v1). The parts-db app completed the same move as a pilot (Parts-DB ADR 0003), and this ADR follows it wherever it fits.

**Owner's decisions recorded here:**
- **Hold lifted.** `PHASES_11.md` put this work on hold until the tax adviser accepted the report. On 2026-11-27 the owner confirmed that **the tax adviser accepted the report**, so the hold is lifted.
- **"SQLite, no extra databases" is superseded** (plan decision 2, confirmed by the owner on 2026-11-27). The app may use the shared PostgreSQL container as a client. It does not run a database server of its own. `CLAUDE.md` and `docs/architecture.md` are amended in Phase 38.
- **No other reader** touches the SQLite file or the uploads folder (owner, 2026-11-27).

## Decisions (proposed)
1. **Storage.** `data`, `uploads` and `backups` move to `/u01/data/tax-healthcare-tool`, and builds move to `/u01/apps/tax-healthcare-tool/build`, with `TMPDIR` for image builds on `/u01`. `config/env`, the Podman image storage and the secrets stay on the eMMC. The paths inside the container (`/data`, `/uploads`, `/backups`) do not change, and stored originals are referenced relative to `UPLOAD_DIR` (verified: no absolute path is stored), so nothing in the database changes when the files move.
2. **Switch and marker.** `config_root` (`~/tax-healthcare-tool`: `config/env`, `config/storage_location`, `DEPLOYED`) never moves. `legacy_root` (the same home folder) holds the old `data`, `uploads`, `backups` and `build`. `storage_root` is `/u01/data/tax-healthcare-tool` and `build_root` is `/u01/apps/tax-healthcare-tool/build`. `data_root` and `build_base` are derived from `use_u01`, which **defaults to `false`** in `infra/group_vars/all.yml`. Parts-DB defaulted to `true` and needed a "do not deploy" warning. Here, merging and deploying change nothing: a test compares the units rendered with `use_u01: false` byte for byte with those of the previous release (`core/testdata/legacy-units/`). A marker file `config/storage_location` (`u01` or `legacy`) records the real state on the server, and the shared check `infra/tasks/storage-check.yml` refuses before changing anything when the marker and the variable disagree, when `/u01` is not a mount point, or when the folders are missing or not owned by `homeapps`. It runs first in `deploy`, `restore`, `restore-drill`, `rollback`, `fetch-backup`, `verify-migration` and `migrate-from-rootful`, and `status` shows the marker. A missing marker means `legacy`. `make relocate-storage` stops the backup timer and the app, takes a `pre-relocate` backup, copies with `cp -a` into empty folders, compares the file lists and the SHA-256 of every file (both lists kept in `config/relocation-<time>/` on the server and in `local/relocation/` on the Mac), and switches only after the owner types `SWITCH`. A failure, or no confirmation, restores the old marker and units and restarts the app and the timer on the old folders. `make rollback-storage` (confirmation `ROLLBACK`, safety backup `pre-rollback-storage` on `/u01` first) points the units back. Nothing is deleted: the old folders stay until the owner removes them.
3. **Where the owner switches.** `use_u01` and `use_postgres` are set as **host variables on the `tax-service` line** of the git-ignored `infra/inventory.ini`. `[taxtool:vars]` does not work for these two: a value in `group_vars/all.yml` takes precedence over it (verified with ansible-core 2.20.10).
4. **Guard.** In the /u01 layout, the app unit and the backup service carry `ExecStartPre=/usr/bin/mountpoint -q /u01`, `Restart=on-failure` and `RestartSec=10` in `[Service]`, and `StartLimitIntervalSec=0` in **`[Unit]`**. This deliberately and openly differs from the wording of contract v1, which puts all four in `[Service]`. On the server (systemd 257), `postgres.service`, `parts-db-web.service` and `parts-db-backup.service` log `Unknown key 'StartLimitIntervalSec' in section [Service], ignoring` and run with the default limit (10 s / 5 starts). This repository follows the contract's intent (no start limit) in the place systemd reads. Correcting the contract and the other two repositories is for their own sessions. The legacy layout renders today's unit unchanged.
5. **Database settings.** If `DJANGO_DB_HOST` is unset, the app uses SQLite exactly as today. Otherwise it uses PostgreSQL from `DJANGO_DB_HOST`, `_PORT` (5432), `_NAME`, `_USER` and `_PASSWORD`, all required in production. Connections use `CONN_MAX_AGE=60`, `CONN_HEALTH_CHECKS=True` and `connect_timeout=5`, and the password never reaches a log. The password arrives only as `Secret=taxtool-db-password,type=env,target=DJANGO_DB_PASSWORD`.
6. **Driver and image.** `psycopg[binary]==3.3.8` (a cp314 wheel exists, so no `libpq5` is needed) and `postgresql-client-17` from Debian 13 (17.12, not older than the server). The build fails if `pg_dump`/`pg_restore` are missing or older than 17.
7. **Unit.** When `use_postgres` is true, the unit gets `Network=db.network` in addition to `gateway.network`, `Wants=postgres.service`, `After=postgres.service` (not `Requires=`), the `Secret=` line and the database variables, and `DJANGO_DB_PATH` is dropped. One-off `podman run` commands get the matching flags. The deploy checks first that `db.network` and the secret exist, by name only.
8. **Migration method.** `migrate` on the empty `taxtool` database, then `dump_exact` (a dumpdata with full-precision timestamps and exact decimals, because every live timestamp has a fractional second), then `loaddata`, then a sequence reset. `contenttypes` and `auth.permission` are recreated by `migrate`, and sessions are dropped. The user with its password hash, `admin.LogEntry` and every `core` primary key are kept. `pgloader` and a custom copy were rejected (see the findings, section 4).
9. **Proof.** An engine-neutral `data_fingerprint` (normalised decimals, UTC timestamps, sorted-key JSON, natural keys), `report_checksums` (a SHA-256 per CSV report and year, with `generated_at` fixed), a stored-originals check (`locate` state and SHA-256 against `ImportBatch.sha256`, per member for zips) and `decimal_check` must all match or be zero. They print counts and hashes only. A rehearsal in `taxtool_rehearsal` comes first. That database is created and dropped on the platform side, because the role has no `CREATEDB`.
10. **Ordering.** Every text order that a page, report, CSV, PDF or ZIP shows is sorted in Python with one engine-independent key (as in parts-db `parts/ordering.py`). The JSON provenance display gets an explicit field order. These are tested with umlauts, mixed case and numbers on both engines, plus a golden report test.
11. **Backups.** The app's own `backup_db` keeps producing one verified archive holding the database (`pg_dump -Fc` from an exported snapshot in a REPEATABLE READ transaction, row counts through the ORM in the same transaction) and the uploads, with the same names and retention. The platform's nightly dump is a second layer, not a replacement, because it holds no uploads. Restore drills and swaps use the platform's `pg-restore-drill` / `pg-restore`.
12. **Rollback and retention.** After the cutover, the SQLite file is moved (not deleted) to `/u01/data/tax-healthcare-tool/legacy-sqlite/` and kept until the next tax return and SBK assessment that use the migrated data are filed. The home-folder copies are kept until Phase 39 is verified. The owner removes both.

## Consequences
- The backup service in the /u01 layout is retried every 10 s, without a limit, whenever it fails, not only when the disk is missing. A persistent backup failure therefore repeats until fixed. It is visible in the journal and costs a container start each time, but it never deletes anything (contract v1, as in parts-db).
- Tests that assert the old mounts, `Restart=always`, `DJANGO_DB_PATH` and the SQLite-only fingerprint change deliberately in Phases 36 and 38 (list in the findings, section 7).
- `iexact`/`istartswith` and the `Lower('name')` uniqueness become Unicode-aware on PostgreSQL. The current data has no non-ASCII names and no collisions.
- SQLite's 15-significant-digit limit on stored decimals no longer applies. No current value reaches it.
- The image grows by the PostgreSQL client tools.
- Until the owner adds `/u01/data/tax-healthcare-tool/backups` to the platform's offsite paths, this app's archives are not offsite. They are not offsite today either.

## Phase 38 record (code only, not deployed)
- **Settings** (decision 5) as specified. In production all five variables are required when `DJANGO_DB_HOST` is set, and `DJANGO_DB_PATH` only when it is not. `USING_POSTGRES` and `DJANGO_PG_BIN_DIR` were added.
- **Driver:** `psycopg==3.3.8` with `psycopg-binary==3.3.8`, both pinned (a cp314 wheel exists). **Image:** `postgresql-client-17` from Debian 13, with the build-time version check.
- **Ordering** (decision 10): the owner chose (2026-11-27) to keep today's order. All displayed text orders are sorted in Python by Unicode code point, which equals SQLite's byte order, so nothing visible changed. parts-db's natural order (case and accents ignored) would have moved 14 of the 35 live organisations. This differs knowingly from Parts-DB ADR 0003 decision 12. Places changed: the organisations and categories pages, the name suggestions, the report filter check boxes, the payments page, the tax summary's payment order and its unused-categories line, the country proposals, and `tools/broker_summary.py`. The provenance list follows the import column order, not the stored JSON key order.
- **Fingerprint** (decision 9): engine-neutral and through the ORM (`core/services/fingerprint.py`). `--raw-sqlite` keeps the byte-level format recorded in Phase 37, so those values stay comparable. The engine-neutral hash of the same data differs from the raw one by design.
- **Migration helpers:** `dump_exact` (natural keys only for content types and permissions; every primary key kept, users included) and `load_exact`. `load_exact` was added because `migrate` on an empty database seeds seven categories that would collide with the loaded ones. It removes exactly those, and only from an otherwise empty database, then loads and resets the sequences in one transaction. `pg_sequences` checks the sequences.
- **Checks:** `report_checksums`, `stored_files_check` and `decimal_check`. ImportBatch.sha256 is the hash of the stored file, a zip included, so the whole-file hash covers every zip member; each member's CRC is checked as well.
- **Backups and restores** (decision 11): as specified. The app never creates or drops a database. `--skip-if-empty` lets the pre-deploy backup pass on a database without tables.
- **Units** (decision 7): as specified. One-off runs join only `db` (not `gateway`). The backup service also waits for `postgres.service`.
- **SQLite limit found:** Django reads SQLite decimals with 15 significant digits. The golden data set therefore stays within 15 digits, and a PostgreSQL-only test proves the full field sizes (16/4, 20/10, 20/6) exactly.
- **Test results (2026-11-27):** `make test` passed: 1106 tests, OK, 4 skipped (owner-only samples and Ansible-less paths). `make test-pg` against a throw-away PostgreSQL 17 (Postgres.app) also passed: 1106 tests, OK, 2 skipped (owner-only samples). On PostgreSQL the golden fingerprint, the golden report checksums, the exact-export round trip at full field sizes and the `pg_dump` archive tests all passed, with the same pinned values as on SQLite.
- **Tests changed for PostgreSQL:**
  - `test_prefix` used the hard-coded id 1; it now uses the created payment's id, because sequences do not restart between tests.
  - `core.tests` SQLite-path tests now ignore an inherited `DJANGO_DB_*`.
  - `test_report_package` K6 keeps the test connection open when it closes a streaming response inside the test transaction. This is a Django test-client effect; the app is not affected.
  - The fingerprint, backup and restore commands now decide by the configured engine rather than the start-up flag.
