# CSV import (Phase 5)

One file format, modelled on the app's own payment fields. There are no per-institution profiles: prepare the CSV by hand (e.g. in a spreadsheet) in this format. PDF dividend statements are described in the section "PDF statements" below.

Nothing is imported at upload. Every row is reviewed, problems are fixed or excluded, and an explicit confirmation creates all payments in one transaction.

## File format
- The format is the same whatever the interface language is (comma, decimal point, ISO dates, English column names).
- UTF-8 text (a BOM is accepted), comma-separated, first row = column names. Column order is free; names are case-insensitive. Fully blank rows are ignored. Quoted cells may contain commas and line breaks.
- Dates `YYYY-MM-DD`. Amounts are plain numbers with a decimal point (`1234.56`), at most 4 decimal places, no thousands separators, currency symbols or exponents.
- Maximum 2 MB and 5,000 data rows (`IMPORT_MAX_BYTES`, `IMPORT_MAX_ROWS` in settings).

| Column | Required | Notes |
|---|---|---|
| `payment_date` | yes | Determines the reporting month |
| `organisation` | yes | Matched ignoring case/extra spaces; unknown names are created on commit (flagged as *new* in the review) |
| `category` | yes | Same matching as organisation |
| `currency` | yes | EUR, GBP, AUD or USD |
| `gross_amount` | yes | Must be positive, or negative (a loss) only when the row's category exists and is marked *may be negative*; otherwise the row is invalid and names the category. Corrections/reversals are entered in the app, not imported |
| `frequency` | yes | `monthly`, `quarterly`, `half_yearly`, `yearly`, `one_off` (case and `-`/space variants accepted) |
| `net_amount` | no | Same sign rules as the payment form |
| `withholding_tax`, `expenses` | no | Non-negative, in the row's currency; empty means 0. With these columns in the file, a row that has a `net_amount` must satisfy gross = net + withholding_tax + expenses exactly, otherwise the row is invalid and the message shows the three numbers. A file **without** either column (the format before Phase 10) still imports: a gross/net difference is then imported as *unallocated* and flagged with a note on the row; editing the row in the preview applies the strict rule |
| `income_period_start`, `income_period_end` | no | End must not precede start |
| `comment` | no | Free text |
| `exchange_rate` | no | EUR per 1 unit of `currency`. Stored as a **manual** rate. Not allowed for EUR rows. Leave empty to have the ECB rate looked up |
| `rate_date` | no | Date the typed rate applies to; defaults to the payment date; only valid with `exchange_rate` |

Unknown columns are ignored with a warning. A downloadable template with synthetic rows is on the Imports page (`/imports/template.csv`).

Rows are validated with the same rules as the payment form: the CSV row is turned into an unsaved `Payment` and run through the model's `full_clean`, so import and manual entry cannot disagree. Inactive organisations/categories make a row invalid.

## Workflow
1. **Upload** (`/imports/`). The original file is stored under `UPLOAD_DIR` (default `local/uploads/imports/`, git-ignored, owner-only permissions) with a generated name; the user's file name is only displayed. Rows are staged; no payment, organisation, category, month or rate record is created. Uploading a file with the same SHA-256 as a committed import shows a warning.
2. **Review** (`/imports/<id>/`). Each row shows its status, messages, new-organisation/category flags and a **proposed conversion** (rate, rate date, source, EUR amount, or "no rate" with the reason). Weekend/holiday rate dates are labelled as in manual entry. Rates are requested once per distinct currency and date (and reuse rates already stored).
3. **Fix**: edit a row (re-checked immediately; the uploaded values stay on record), exclude/include a row, keep a flagged duplicate, or ask for exchange rates again.
4. **Confirm** (`/imports/<id>/commit/`): a summary of payments to create (with/without a rate), duplicates skipped/kept, excluded and invalid rows, and any new organisations/categories. Import is blocked while any non-excluded row is invalid.
5. **Commit**: all payments are created in one transaction or none are. The rates saved are exactly the ones shown in the review (no second lookup). Each payment links to its `ImportBatch` and `SourceDocument` and gets an initial conversion event ("Import batch #n, line m") with full rate provenance. Rows without a rate are saved **unconverted** and appear in Reconciliation. Submitting twice imports once.
6. **History**: batches, status, counts and a login-protected download of the original file. Discarding a not-yet-imported batch deletes its staged rows and the stored file.

## Duplicate rule
A row is a possible duplicate when another payment, or an earlier non-excluded row in the same file, has the same **payment date, organisation, currency and gross amount** (organisation compared ignoring case/spacing; amount to 4 dp). Duplicates are never dropped silently: they are skipped on commit unless you choose "Keep anyway". Excluding the earlier row stops it counting as the original. Category, net amount and comment are not part of the rule.

## Errors and edge cases
- File-level problems (not UTF-8, binary data, missing required columns, duplicate header names, no data rows, too large, too many rows) are reported on the upload page and create no batch.
- A row with more cells than the header is invalid until edited.
- If a rate lookup fails, the row stays valid, shows "No rate: ...", and would import unconverted; you can retry with "Request exchange rates again", add `exchange_rate` in the row, or accept unconverted.
- If data changes between review and commit so a row is no longer valid (e.g. an organisation was deactivated), the commit is refused and nothing is imported.

## PDF statements (Phase 14, ADR 0014)
Select one or more PDFs (not mixed with a CSV) on the Imports page, or use "a whole folder" to upload a folder together with all its subfolders in one go (hidden files such as `.DS_Store` are ignored; up to 300 files per upload). A file chooser cannot select files across several folders, so the folder option is the way to upload a tree like `Securities/<issuer>/...`. They are read into the same review as a CSV: one row per statement, per-row edit and exclude, the duplicate rule, a confirmation page, an atomic commit that cannot run twice, history, and a protected download of the original (a single PDF, or a zip of the staged originals).

**What is read.** Text PDFs of Australian dividend and distribution advices whose amounts are in Australian dollars. Per statement: payment date, the payer, recorded as the organisation "<company name> (<ASX code>)" (the name is used only when the statement itself prints it next to its ABN; otherwise just the ASX code; nothing is looked up externally; change it in the review if you prefer another name), the dividend paid (the total payment: this is *gross*), the amount paid (*net*) and the tax withheld. Category `Dividends`, currency `AUD`, frequency `one_off` (dividends are irregular and never treated as recurring); the exchange rate is proposed exactly like for CSV rows. Franked/unfranked amounts and franking credits are Australian-tax information and are deliberately not read.

**Withholding tax is never assumed.** It is `gross - net`, and a non-zero difference is accepted only if a withholding-tax line on the statement states that same amount; otherwise the statement is refused. (In all 54 supplied statements the difference is 0.)

**Where each value came from.** Every row lists, per field, the page and the source line (long digit runs such as reference numbers are hidden). Values that several parts of a statement must agree on (the amount paid, the total payment) are refused when they disagree.

**Refused with a reason, nothing staged:** not a PDF, damaged, password-protected, no text layer (a scan; OCR is out of scope), not a dividend advice, amounts not in AUD, payment date or amounts missing or ambiguous, gross and net not explained. Recognised but not importable as a dividend: *scheme consideration* payments (shares sold in a takeover: record as a sale) and *bonus share plan* statements (shares instead of cash). A dividend reinvestment plan statement (for example Woolworths) is staged with a comment "reinvested ... (no cash received)", because the dividend is still paid; exclude the row in the review if you do not want it. Statements that were uploaded together but not recognised are listed as warnings, the others are staged.

**Revolut "Flexible Cash Funds" statements** (the interest-bearing Revolut account: a money-market fund) are read too, one statement per month. Per statement: gross = *Total Earned Return*, expenses = *Total Fees* (the service fee charged), net = gross - expenses, withholding 0 (none is shown), payment date = last day of the period, category `Interest`, frequency `monthly`, currency from the statement (EUR: rate 1). The daily "Return PAID" and "Service Fee Charged" lines must add up exactly to the summary totals, otherwise the statement is refused. The ordinary Revolut *account statement* (transfers and card payments) contains no income and is refused as "not recognised". Whether this fund return is "interest" or a fund distribution for German tax is an open question (`docs/rules/README.md`, item 12); the app records it as Interest, which the owner can change per row.

**Layouts.** The registries (Computershare, MUFG, Automic and company-specific advices) print the same figures in different arrangements, and the PDF text order differs: labels first and values later, values one per line, column headings with a totals row. The reader looks for the same few anchors in all of them (a labelled net payment, the largest amount of the holding table, labelled withholding, labelled payment date, the ASX code) instead of one parser per company, and requires them to agree. Statements of other kinds (bank account statements such as Revolut, broker interest statements) are not income advices in this sense and are refused as "not recognised".

## PDF statements: readers, multi-row results and the inventory tool (Phase 15, ADR 0015)
**Readers.** `core/services/statement_readers.py` holds an ordered list of readers (`READERS`). Each has an id, `recognises(pages)`, `parse(pages)` and a flag `needs_layout` (such a reader is given pypdf's layout-mode text, which keeps table cells on one line). Exactly one reader may claim a file. A file claimed by two is refused with a message naming both reader ids; a file claimed by none is refused as not recognised. Registered now: `revolut_flexible_cash_funds` and `au_dividend_advice` (the Phase 14 readers, unchanged). A reader that recognises a file and then cannot read it safely refuses it with its own reason.

**Results.** A reader returns a result with `rows` (the import columns plus, per field, the page and source line), `notices` (information for the review; never amounts or names from the document beyond the figures shown), a `fingerprint` and, if known, the statement `period`. Every row is staged with its own source file name and provenance; line numbers run 1, 2, 3 ... across the whole batch. Three outcomes are not errors: **staged**; **nothing to import** (recognised, no income); **recognised and not imported** (for example a stock sale; shown as a notice). They are reported as one summary line each with a count ("12 statements recognised, no income."), not one warning per file. An upload in which every file is of these kinds creates **no batch** and shows that message. A file that is refused (or unrecognised) is still listed as "Not staged ... (reason)". The Phase 14 behaviour is kept: sorted processing, same-file detection by hash, atomic creation, the stored original (a single PDF or a zip), the warning about a batch already committed.

**Fingerprints.** Two files in one upload with the same reader id and the same non-empty fingerprint are one statement: the first is staged, the other is listed as "same statement as <file>". This catches re-issued statements whose bytes differ. Each reader decides its fingerprint; it must be built only from identity fields of the statement. Revolut Flexible Cash Funds: currency, period end, total earned return and total fees. Australian dividend advices: none (an advice has no statement number that is read, and two holdings can pay equal amounts on one day), so the existing row duplicate rule is the safeguard.

**Displayed file names.** Digit runs of six or more in a file name (account or statement numbers) are masked as `######` in the review, the history and the batch name; the stored original keeps its own generated name and bytes.

**Amount conventions** (`core/services/amounts.py`, used by the later bank and broker readers): `parse_amount_us` ("1,234.56", "$1,234.56", "(1,234.56)" negative, a dash or em dash is zero), `parse_amount_uk` ("1,234.56", "£1,234.56", "-3.10"), `parse_amount_de_with_hs` ("1.234,56 H" credit, "1.234,56 S" debit; the H or S is required). Anything else raises ValueError, so a reader refuses the statement.

**Damaged cross-reference table (Phase 22).** A file pypdf cannot open goes once through `pdf_text.repair_xref_counts`, an in-memory fix of one defect: a cross-reference subsection header that declares fewer entries than the table lists (the MECU files). Only that count is corrected; the result is never stored (the uploaded original is kept byte for byte), a table that is not intact stays refused, and an undamaged file never goes through it. The PDF size limit is 16 MB (one MECU statement is 12 MB).

**Layout extraction that fails.** A reader that needs layout text only sees the file if layout extraction works; when it returns no text (it can, for files whose default text is fine) the file is simply not claimed by layout readers and the plain-text readers still read it.

**Encrypted PDFs.** A PDF encrypted only against editing (empty user password) is opened with the empty password. AES-encrypted files (the RVB statements) need the `cryptography` package, which is pinned in `requirements.txt` since Phase 16 (owner decision, with its two dependencies `cffi` and `pycparser`). If it is ever missing, such a file is refused with a message saying so; a PDF with a real password is refused as password-protected.

**Inventory tool.** `.venv/bin/python tools/pdf_inventory.py <folder> [--recursive]` reads every PDF with the same readers and prints one line per file: masked name, reader id or "unrecognised", the statement period if the reader found one, number of income rows, number of notices, outcome (staged / nothing to import / recognised, not imported / refused with the reason) and flags: *same content as <file>* (same extracted text or same reader fingerprint), *period gap of N day(s)* or *period overlaps* against the previous statement of the same reader, *file name period differs from the period read*. It prints no amounts and no names from the documents, does not touch the database, and ends with a count per outcome.

## HSBC UK savings statements (Phase 16, ADR 0016)
Reader id `hsbc_savings` (GBP; the Flexible Saver), read in layout mode. **Recognised by structure:** a table with paid out / paid in / balance columns (the words are matched with spaces removed, because some headings are letter-spaced), a "BALANCE BROUGHT FORWARD" row and a "BALANCE CARRIED FORWARD" row, the pound sign, and at least one "GROSS INTEREST" or "INTERNET TRANSFER" row. **One payment per "GROSS INTEREST" credit:** payment date = the credit's date in the date column (two-digit year, so 05 Jan 25 is 2025-01-05); `income_period_end` = the date in the following "TO <ddMONyyyy>" line, `income_period_start` empty (the statement prints only the end); GBP, category Interest, frequency monthly, organisation `HSBC UK (Flexible Saver)`, comment "Gross interest (PDF import).", gross = the credit, expenses 0, net = gross, withholding 0. Withholding is 0 only because the running balance proves the credit was paid in full. **Not staged:** internet transfers in either direction (not income; the direction is taken from the balance). **Provenance:** page and both source lines (the credit line and the TO line).

**Arithmetic (a failure refuses the statement, naming the row position, never the figures):** for every row, previous balance plus or minus the amount equals the balance (an interest credit must raise it by exactly its amount); a table that continues on another page has one brought/carried-forward pair per part and the balances must chain; opening and closing balance come from the first brought-forward and last carried-forward row; the summary block (opening, payments in, payments out, closing) is an optional second check used only when all of a figure's label is readable, and a readable figure that disagrees refuses the statement. A row without a date is not recognised as a row, so a credit missing its date breaks the balance chain and the statement is refused rather than a credit being lost. **Unknown rows:** any other row type (a charge, a different credit) refuses the statement naming the type text, with digits removed. No fee line exists in the samples, so none is understood.

**Continuity (warnings only).** When several statements of one account (same sort code and account number, never shown) are uploaded together, each is compared with the previous one by sheet number: *sheet numbers skip from A to B, but the balances connect* (the sheet number is not a plain count of statements: in the samples it skips while the balances connect, so no money movement is missing), *... and the balances do not connect: a statement may be missing*, or *overlap*; and the opening balance against the previous closing balance. **Fingerprint:** sheet number, closing balance and period end, so a re-issued statement is staged once.

## RVB current-account statements (Phase 17, ADR 0017)
Reader id `rvb_giro` (EUR), read in layout mode. **Recognised by structure:** one "alter Kontostand" row and one "neuer Kontostand" row with German amounts (H credit, S debit). The bank's name, address and header wording are never used (the name changed in 2026 and is sometimes rendered as noise); the organisation is the fixed name `RVB (Girokonto)`. Booking lines are `dd.mm. dd.mm. <text> PN:<posting number> <amount> H|S` (booking date, value date), with detail lines below.

**Every statement is proved:** alter Kontostand + credits - debits must equal neuer Kontostand, so a damaged statement is refused, never reported as empty. **Ordinary statements** (transfers, standing orders, credits, prizes) have nothing to import; the booking texts `Gutschrift`, `Umbuchung`, `Dauerauftrag` and `...-Überweisung` are recognised only to say they are not income. A `Gutschrift` whose detail lines say "Gewinn" or "Los" (the savings lottery) adds the notice "Savings-lottery prize credit, not imported."; any other `Gutschrift` adds "A credit (Gutschrift) that is not interest, not imported." Notices contain no amounts; the same notice from many statements is shown as one line with a count. **Any other booking text refuses the statement** naming the text (digits removed), for example a fee: bank and Revolut fees are expected on accounts other than the interest-bearing one used for the samples, so such a statement is refused with the text named until an example layout is supplied.

**Interest closing** (detected by the booking `Abschluss lt. Anlage 1` and its Anlage 1 block, never by the statement number or file name): one payment. Payment date = the booking date (the year is taken from the statement; the value date is written to the comment); income period = "Kontoabschluss vom ... bis ..."; EUR, Interest, quarterly; gross = the sum of the HABENZINSEN lines, which must equal the booked closing amount and "Summe Abschlussposten"; expenses 0 (a debited fee line in the block refuses the statement); withholding = the booked `Kapitalertragsteuer`, `Solid.-Zuschlag` and `Kirchensteuer` debit lines together, net = gross - expenses - withholding. The comment names each tax with its amount ("Withholding as booked: Kapitalertragsteuer 10.00 + Solidaritätszuschlag 0.55.") and states the base ("Tax charged on 40.00 of the 50.00 interest."): a base smaller than the interest means part of the interest was not taxed; the app records what was booked and does not say why. The tax lines of the Anlage 1 block must agree with the bookings, the stated base must not exceed the interest and must agree under each booking, otherwise the statement is refused. No Kirchensteuer example exists in the samples; its line is recognised by the word `Kirchensteuer` and covered by a synthetic test only.

**Fingerprint:** statement number, year, closing balance and closing date, so a re-issued statement (identical text, different bytes) is staged once. **Continuity:** all recognised statements of the account (same account number, never shown), income or not, are chained by balance; a statement whose opening balance differs from the previous closing balance is warned about.

## E*TRADE client statements (Phase 18, ADR 0018)
Reader id `etrade_client` (USD), read in layout mode. **Recognised by structure:** "CLIENT STATEMENT", "For the Period ...", the "CASH FLOW ACTIVITY BY DATE" table and the "INCOME AND DISTRIBUTION SUMMARY". The period (one or two calendar months, possibly across a year end: "December 1- January 31, 2026") gives the year of the "m/d" dates; a date outside the period refuses the statement.

**One payment per income event.** A `Dividend` line is a money-market-fund dividend (frequency monthly); a `Qualified Dividend` line is a company-stock dividend (frequency quarterly). A `Tax Withholding` line with the same date and the same description belongs to it: gross = the dividend, withholding = the withheld amount (positive), net = gross - withholding, expenses 0. Currency USD, category Dividends (owner decision; the German classification is open, rules README item 12), organisation = the description printed on the income line tidied by the shared function (`organisations.tidy_security_name`, the same string for the same security from any broker), comment "Fund dividend via E*TRADE." or "Qualified dividend via E*TRADE.". **Never assumed:** a company-stock dividend without a withholding line, a withholding line without a dividend, two withholding lines for one dividend, or any other activity type (interest, return of capital, adjustment ...) refuses the statement, naming the type. `Bought`, `Sold` and `Journal` lines and a "Securities purchased/sold" section are listed as a notice (type and date only), not imported. Amounts: parentheses are negative, a dash is zero.

**Prior-year items.** A fund dividend the statement marks "Transaction Reportable for the Prior Year" (it falls in the first days of January) is recorded with its printed date and the comment "The statement marks this transaction as reportable for the prior year."; the statement's own period totals leave it out, so the reconciliation does too.

**Reconciliation (each failure refuses the statement):** the lines add up to "NET CREDITS/(DEBITS)"; the sweep table (automatic investments of the cash into the fund) adds up to the same net (skipped with a notice if there is no sweep table); the income summary's "Qualified Dividends", "Other Dividends" (absent = 0) and "TOTAL INCOME AND DISTRIBUTIONS" for the period equal the sums of the lines by class; the account summary's "Tax Withholdings" equals the sum of the withholding lines (skipped with a notice if the row is absent). **Messages:** nothing after the "MESSAGES" heading is ever read, kept, logged or shown (it can contain sensitive text); a test checks that a fake password there reaches no row, provenance, notice, log or staged data. **Fingerprint:** period and the ending total value, so a re-issued statement is staged once.

## Fidelity Stock Plan Services reports (Phase 19, ADR 0019)
Reader id `fidelity_stock_plan` (USD), read in layout mode. **Recognised by structure:** the report title, a period line "<Month d, yyyy> - <Month d, yyyy>" and the "Account Summary". Reports cover one or two months; a month with only core-fund activity has nothing to import.

**One payment per "Dividend Received" line** of "Dividends, Interest & Other Income": date (MM/DD, the period's year), the security as printed (capitals; the code column is removed; a name wrapped onto the next line is rejoined), gross = the amount. Category Dividends, USD, organisation = the shared tidy function (the same string a broker-neutral company gets from E*TRADE), comment "Dividend via Fidelity." or "Fund dividend via Fidelity." (a security named in the Core Fund Activity table is a core fund: monthly; any other is a company stock: quarterly). Any other income description (interest, capital-gain distribution, return of capital) refuses the statement naming it.

**Withholding is settled across the upload (the "Taxes Withheld" table).** "Non-Resident Tax" is negative, "Adj Non-Resident Tax" positive (a reversal); a flag letter in front marks a prior-period item, and the date printed is the date of the event the posting belongs to (so a January report holds December and November postings). All files of an upload are read first, then each event's withholding = minus the sum of every posting for it (same security, same date, names matched by their common start because the tax table prints a longer form of a wrapped fund name): original, reversal and re-booking all count. **Warnings** on the batch: "Tax postings for events not in this upload: n (not staged)." (the postings are counted, nothing is staged for them); a net tax refund larger than the withholding (withholding recorded as 0, row comment, count in the warning). **Comment marks:** "Withholding is the sum of n postings (m reversal(s))." when several postings were combined; "Withholding may be revised by a later statement." on the rows of the latest statement of the upload (a statement outside the upload could still book a posting for them); a statement uploaded alone is therefore always marked. The withholding shown in the review is the settled value; its provenance lists every posting with the file it came from.

**Reconciliation (each failure refuses the statement):** the income lines equal "Total Dividends, Interest & Other Income" and the income summary's period total (skipped with a notice if the summary is absent); the tax lines equal "Total Federal Taxes Withheld" by absolute value, because the printed total changes sign (never used as an anchor). The Core Fund Activity table is read only to identify the core fund: cash movements ("You Bought", "Reinvestment", "You Sold", transfers) are never income. A quantity reconciliation of the core fund is not done: the report prints only the ending quantity, not the beginning. Rounding: the importer never compares a rate to an amount, so no tolerance is needed.

**Deliveries, sales and journals (owner: out of scope, taxed when employed).** Lines of "Securities Bought & Sold" and "Other Activity In/Out" are listed as notices ("Not imported: shares bought (a delivery or purchase) on 09/12.", "shares sold", "other activity (a journal)": type and date only) and nothing is imported from them. Fingerprint: period and ending account value.

## Managing-agent rental statements (Phase 21, ADR 0021)
Reader id `hodges_rental` (AUD), named after the sample folder; it is not tied to one agent. **Recognised by structure:** a "Tax Invoice" with "Statement #", "Money In", "Money Out" and "You Received" figures; the agency name, address and logo text are never used. Text mode: the default (it keeps the wrapped rent lines together as well as layout mode does).

**One row per statement.** Gross = the rent received (the amount of each "Rent paid to <date> ..." receipt; a statement can hold two, the printed period then spans both months). Expenses = every cost line listed before "Total" (management fee, repairs, council and water rates ...) plus the sundry fees printed after it; withholding 0; net = gross - expenses = "You Received". Payment date = the **statement date**; income period = the day after "previously paid to" up to "paid to" (a short final period is read as printed); currency AUD, category Rental, frequency monthly, comment "Rental statement (PDF import)." and, when lines are flagged `*` (GST-inclusive), their count: the app records no GST split. **Organisation** = the setting `DJANGO_RENTAL_ORGANISATION` (environment variable, owner decision: the managing agent); it is never in code, and an unset value refuses the statement with a message saying so. It must be set where the app runs (locally in the shell or `.env`; on the server in the unit's environment when deploying).

**The statement must close (a failure refuses it, naming the block, never the figures):** Money In minus Money Out = You Received; the rent receipts add up to Money In and to the second figure of the "Total" line; the cost lines add up to the first figure of the "Total" line; costs plus sundry fees = Money Out. The "Total" line excludes the sundry fee, so it is only one of these checks. **Never staged:** the owner withdrawal (a payout of money already received) is recognised and mentioned in a notice (count and statement date); the balance and GST-summary lines are ignored. **Refused naming the label:** a money-in entry that is not rent, an "arrears", "advance" or "prepaid" line, and any unrecognised line with an amount after "Total". **Fingerprint:** statement number, period end and the You Received figure.

## MECU account statements (Phase 22, ADR 0022)
Reader id `mecu_account` (AUD), layout mode, organisation `MECU` (fixed). **Recognised by structure:** account sections with the Effective / Posted / Description / Debit / Credit / Balance columns, an opening and a closing balance per account and a statement number; the bank's name, address and branch text are never used and no account number is stored. An account that continues on the next page ("Account: <same number> ... continued") is one account. Several accounts (savings, term deposits) in one statement are normal.

**Dates (M2)** carry no year: the year comes from "Statement Date" (a December date in a January statement is last year's); the period runs from the earliest opening-balance date to the statement date and must be at most 45 days; a posted date outside it (or an effective date more than 7 days before it) refuses the statement. Periods are always taken from the content: file names are not trusted (two of the samples carry each other's month; the inventory flags them).

**Arithmetic (M9).** The statement prints one amount column; credit or debit is derived from the running balance, which must be proved for every row, and opening + credits - debits must equal each account's closing balance, or the statement is refused. Rows that only restate the balance (a dormant-account note, a balance enquiry, an invalid-PIN note) are accepted only when their single figure equals the running balance.

**Interest rows (payment date = Effective date; the Posted date goes in the comment).** One row per "Interest Credit" and per "Bonus Interest" (separate rows), category Interest, AUD, monthly. The memo lines under it, "Overseas Withholding Tax ($x)" and "Gross Interest. ($x)", give withholding and gross (gross = the credit when there is no memo); gross - withholding must equal the credit, else the statement is refused (M4). The comment names the kind (interest, bonus interest, term-deposit interest) and the account type (savings account, term deposit) only. **Term deposits (M5):** interest is staged from the term-deposit section only: the "Interest Credit" at maturity, or the "Interest Payment ... ($x)" paid out by transfer; the receiving "Interest Credit ... Transfer" credit in a savings account is a transfer and is not staged, and it must match a term-deposit payment of the same date and amount in the same statement, else the statement is refused. **Not income (recognised by the first words of the booking):** direct credits, BPAY, Osko, transfers, external transfers, POS, ATM, deposits and similar; any other booking (a fee, for example) refuses the statement naming its first words.

**Annual summary (M6).** A June statement's "Payment Summary for Withholding Tax" (gross interest and non-resident withholding tax of the financial year) is compared, when the upload holds the statements of the whole financial year, with the staged rows: a difference is a warning and the rows still stage; a partial year is "not compared". **Fingerprint:** statement number, period end and the sum of the closing balances. A page without a text layer (barcode pages) does not refuse a file whose other pages have text.

## Ord Minnett Cash Management Trust statements (Phase 23, ADR 0023)
Reader ids `ordminnett_cmt` and `ordminnett_valuation` (AUD), layout mode, organisation `Ord Minnett` (fixed). **Recognised by structure:** a "Date / Description / Debit ($) / Credit ($) / Balance ($)" table that starts with a "Brought Forward" row; the broker's name and address are never used. The holdings snapshot ("Portfolio Valuation") has its own small recogniser and has nothing to import. The Australian dividend reader no longer claims account statements or valuations (a statement with a "Balance ($)" column or a "Portfolio Valuation" is not a dividend advice).

**Direction (O1).** One amount column: credit or debit comes only from the change of the running balance, proved for every row, else the statement is refused. Dates are "dd Mon yy" (two-digit year). **Not income, not staged:** dividend credits and other direct credits (the share advices already cover dividends, O5), tax-office refunds, BPAY, direct debits, transfers and transfers to the holder's own bank account. **Notices (date only, no names, no amounts):** a share-scheme consideration credit, a stock-sale proceeds transfer ("Transferred from ... SELL ...", sales are never imported), and a "large credit" of at least AUD 20,000 that carries no dividend reference (a property sale or similar; this threshold is a heuristic and only decides whether a notice is shown). Any other booking text refuses the statement naming its first words.

**Interest rows are made by a batch step (the reader's `settle`), not per statement,** because the monthly statements and the two financial-year statements overlap and the June-quarter interest exists only in the financial-year file. Exact repeats across statements (same kind, date and amount) are staged once, the first statement by file name wins, and the repeats are listed in the batch warnings (two identical lines inside one statement are two payments). Each withholding debit ("Overseas Withholding Tax") is paired with the interest credit of the same **calendar quarter** (the debit date goes in the comment). Row: payment date = the credit date, gross = the credit, withholding = the paired debit, net = gross - withholding, income period = the calendar quarter, AUD, Interest, quarterly. A withholding without an interest credit in its quarter is a warning and no row; an interest credit without a withholding debit stages with withholding 0 and a warning (never assumed silently). **Taxation summary (O4):** the financial-year statement's quarterly gross interest and non-resident withholding are compared with the lines; a difference is a warning only. **Fingerprint:** period, statement date and closing balance. The inventory tool runs the same batch step, so its row counts are those of an upload of the folder; the financial-year files overlap the monthly ones by design (the "period overlaps" flag is expected for them).

## Australian statements together: rental, MECU, Ord Minnett (Phase 24, ADR 0024)
This section only consolidates; the details are in the three sections above.

| | Rental agent (`hodges_rental`) | MECU (`mecu_account`) | Ord Minnett (`ordminnett_cmt`) |
|---|---|---|---|
| Rows | one per statement | one per interest credit, bonus interest and term-deposit interest | one per quarter's interest (batch step) |
| Category / frequency | Rental / monthly | Interest / monthly | Interest / quarterly |
| Organisation | setting `DJANGO_RENTAL_ORGANISATION` | `MECU` (fixed) | `Ord Minnett` (fixed) |
| Gross / withholding / expenses | rent received / 0 / costs and sundry fees | Gross Interest memo / Overseas Withholding Tax memo / 0 | interest credit / paired withholding debit / 0 |
| Payment date | statement date | Effective date (Posted in the comment) | credit date |
| Fingerprint | statement number, period end, You Received | statement number, period end, sum of closing balances | period, statement date, closing balance |
| Warnings / notices | owner withdrawal (notice) | annual Payment Summary mismatch or not comparable (warning) | repeats across overlapping statements, orphan or missing withholding, taxation-summary mismatch (warnings); scheme consideration, stock-sale proceeds, large credit (date-only notices) |

* **Tolerant opening.** A file pypdf cannot open goes once through an in-memory repair of the one-entry cross-reference defect (MECU); the upload is stored unchanged. The PDF size limit is 16 MB.
* **Dedupe and pairing.** Only Ord Minnett dedupes across statements (exact repeats of overlapping monthly and financial-year statements; the first by file name wins, repeats are listed). Every reader also relies on the row duplicate rule at review (date + organisation + currency + gross) against rows already in the database.
* **Collisions with existing data.** `tools/collision_report.py` (read only, counts only, also written to the git-ignored `local/exports/collision_report.txt`) compares the staged rows with the payments in the database: exact collisions (the review flags them), near collisions (same gross within 3 days under another organisation, or same date and organisation with another gross), rows with no counterpart, and database payments of the same organisation without a staged counterpart. Nothing is changed or deleted; deletion would be a separate decision of the owner.
* **Joint account (Phase 27, ADR 0027).** The same report covers the joint-account rent rows (EUR; needs the rules and the category in the database): exact and near collisions, rows without a counterpart, and database payments of the same organisations in the staged range without a staged counterpart. `--no-file` skips the report file. Collisions with rows of an earlier project are only reported; deleting them is the owner's decision. The inventory over the joint folder shows refusals, balance/period gaps and name-versus-period mismatches (a refusal for a missing category disappears once the category is created).
* **Samples check.** The Phase 14 to 23 sample folders are read by optional local tests that print only counts; `core/test_sample_regression.py` proves that the Phase 14 samples give identical rows through the registry.

## Joint-account statements (Phases 25 and 26, ADRs 0025 and 0026)
The household joint account at the same bank has its own reader `rvb_joint`. It claims a file only when the printed account number equals the setting `DJANGO_JOINT_RENTAL_ACCOUNT` (digits only, never shown unmasked); `rvb_account` steps aside for that account and nothing else. Each statement is proved first (every booking parses, page carries agree, alter + credits - debits = neuer). Then one row is staged per credit matched by a `tenant_rent` rule (EUR, monthly, whole credit, category from `DJANGO_JOINT_RENTAL_CATEGORY`, default `Rental (joint)`, which you create first; organisation = the rule's, created with country DE) and per `service_charge_settlement` credit (one-off). A credit that mentions a Kaution is staged for its Miete figure only when the labelled Kaution and Miete figures add up to the credit (the deposit is a notice); otherwise it is left out with a notice. A credit with the word "Miete" that no rule matches is a notice ("possible rent not matched"). Every other booking, all debits included, is ignored and counted ("N bookings ignored"); rental costs are deferred. A statement with no rent is "recognised, no income". Refusals name page and booking position, not figures. Rules that will decide what is rent are rows of `StatementRule`, edited in the Django admin (`DJANGO_ENABLE_ADMIN=1` outside development); match_on is counterparty, purpose, either (each on its own) or combined ("counterparty | purpose" as one text, so a pattern can use a negative lookahead such as `^(?!.*nebenkosten).*tenant` to keep rent and settlement rules apart); patterns are case-insensitive regular expressions on normalised text (ü, ue and u match each other, hyphens are spaces) with optional validity dates; no name is ever in code or tracked files. `tools/rule_preview.py <folder>` shows, without names or amounts, how many credit lines each rule matches and which lines match several rules; lines matching rules of different kinds or tenants are conflicts and are never staged. A value date such as "30.02." (30-day month) is tolerated.

## Security and privacy
- Login required on every import view; the stored file is served only through a login-protected download with a generated name, `Content-Disposition: attachment` and `nosniff`; stored paths are checked to stay inside `UPLOAD_DIR`.
- Cell contents and amounts are never logged. Cell text is HTML-escaped when displayed.
- Only the currency and payment date are sent to the exchange-rate service (see exchange-rates.md).
- Tests and the template use synthetic data only. PDF tests build their own PDFs (`core/test_pdf_support.py`); the owner's real statements stay in the git-ignored `local/samples/` and are only read by an optional local test that prints nothing.
- PDFs are read inside the app (pypdf); no document or text is sent to any external service.
