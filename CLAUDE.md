# Tax and Healthcare Tool — Standing Instructions for Claude Code

Django web app to record, convert and report personal income from multiple institutions and countries (DE, UK, AU, US). It supports preparing information for German statutory health insurance (SBK) income assessments and the German annual tax return. Single user, developed locally on a MacBook Pro, later deployed in Podman on a Linux server (Ansible) that already runs another Django app.

The app produces general financial summaries. It is NOT an official SBK assessment or tax calculation.

## How to work
- Work one phase at a time (see docs/prompts/PHASES.md for phases 1 to 8, kept for audit and never edited, and docs/prompts/PHASES_2.md for phases 9 to 14). Do only the phase I name. At the end of a phase, report and STOP for my approval.
- At the start of a phase: read README and docs/, inspect `git status` and `git log`, confirm scope, list assumptions and blocking questions, propose steps.
- Ask me when a financial rule or requirement is ambiguous. Never invent financial data, exchange rates, dates or classifications.
- Do not overwrite or discard existing work. Keep changes focused. Make small commits that match completed, tested changes.
- Write tests alongside code, run them, and report actual results (not expected ones).
- Keep it simple: Django templates and plain HTML forms, SQLite, no JS framework, no queues, no extra databases, no unneeded dependencies.
- End-of-phase report: what was implemented, key decisions, files changed, checks run with real results, open issues/assumptions, commands to run/verify, proposed next-phase scope.

## Financial principles
1. Preserve the original transaction. Store amount and currency as reported, plus the rate used and resulting EUR amount. Never overwrite originals when recalculating.
2. Keep source data, currency conversion, monthly normalisation and assessment/tax reporting as separate concerns (separate models/services). Calculation logic lives in testable Python services, never in templates.
3. Use `Decimal` and DecimalFields only. Keep full precision internally; round only for display/export.
4. Reports state their basis: period, currency, gross vs net, actual vs normalised, exchange-rate basis, excluded/missing items.
5. Do not assume a category is taxable, exempt or SBK-relevant. Categories are configurable. Legal rules live in `docs/rules/` as versioned, documented rules with a verification status (verified, unverified, or the owner's input); never implement an unverified rule.

## Currency conversion (decisions made)
- Convention: `EUR amount = original amount × rate` where rate = EUR per 1 unit of original currency. EUR payments always use rate 1.
- Default rate date = payment date (historical). Never silently substitute today's rate, another date or a guess. If a fallback is ever used, label it explicitly.
- Provider: ECB reference rates via Frankfurter, behind a small provider interface so it can be swapped. Verify the API's current behaviour (endpoints, supported currencies, weekend/holiday handling) before coding, and document it.
- Persist per payment: original currency/amount, rate, rate date, provider/source, converted gross/net EUR, status/notes. Rate changes must be auditable. Reports use the stored rate unless I explicitly trigger a recalculation.
- On provider failure: show a clear error, offer manual rate entry, and never lose the user's form input.
- Initial currencies: EUR, GBP, AUD, USD; adding more must not need a schema redesign.

## Frequency and normalisation
Frequencies: monthly, quarterly, half-yearly, yearly, one-off/irregular. Monthly equivalent = amount ÷ 1/3/6/12. State whether gross or net is normalised. One-off items (e.g. capital gains) are never treated as recurring. Support two modes, always labelled: (a) actual payments received in a calendar year, (b) normalised recurring monthly income. An annual total ÷ 12 is an average of actuals, not a recurring figure. Preserve income-period dates separately from payment date when supplied.

## Data model (starting point; improve if justified and document why)
ReportingYear (unique year, notes) → ReportingMonth (unique year+month) → Payment. Also Organisation (name, country, active; avoid duplicate spellings), IncomeCategory (configurable, deactivate rather than delete if referenced; seed: salary, pension, rental, interest, dividends, capital gains, other), ExchangeRateRecord, SourceDocument, ImportBatch.
Payment: month, organisation, category, payment date, optional income period start/end, original currency, gross, nullable net, withholding tax and expenses (Phase 11, ADR 0011: a normal payment may be negative only in a category flagged `may_be_negative`; no loss-offset rule is implemented, see docs/rules TAX-11) (Phase 10, ADR 0010: gross = net + withholding tax + expenses, enforced on create/edit; recorded information only, no calculation uses them), frequency, comment, source doc/import batch, timestamps. Validate dates, amounts, currency codes. Support explicit corrections/reversals. Payment date determines the reporting month by default; keep them consistent on edit.
Deleting a year deletes its months and payments; deleting a month deletes its payments. Both require UI confirmation. Document deletion behaviour in docs/data-model.md.

## UI (Django templates, responsive on a laptop, keyboard-accessible)
- Language (Phase 12, ADR 0012): one app-wide setting, English default or German, switched in the page header; it drives interface text and number/date formats on screen. German report terms come only from `docs/glossary.md`. CSV exports are language-independent (comma, dot decimal, ISO dates, always English headings). Update translations with makemessages + msgfmt and commit the `.po` and `.mo`.
- Visual rules (Phase 13, ADR 0013): colours only as CSS tokens in `core/static/core/base.css` (contrast checked by `tools/check_contrast.py`); no inline `style=`; actions are `.btn` buttons, and anything that changes or deletes data is a POST form button (a delete link only opens its confirmation page); notes and description fields are 4-row growing text areas; report notes sit below the table, the basis block above it; the 14 SBK headings have Popover info buttons fed by `core/glossary.py` (kept equal to docs/glossary.md section A). No dark mode.
- No display-currency selector (removed in Phase 9, ADR 0006). Amounts show in their own currency; reports and totals are EUR at each payment's stored rate.
- Opening page: list years, add year, delete year (confirm), per-year gross/net totals and a clearly labelled estimated monthly figure.
- Year page: all 12 months (including empty), gross/net, payment count, add/delete month, link back.
- Month page: payments table (date, organisation, category, original amount+currency, gross/net EUR, frequency, normalised monthly where meaningful, comment) with add/edit/delete (confirm). Organisation and category are combo-style: pick existing or add new.
- Payment form flow: validate → get rate → show error or manual-rate option → compute and save → confirmation showing original amount, rate, EUR amount. Editing never silently replaces a stored rate; recalculation is an explicit action.
- No dashboards or charts in the first version.

## Imports (built in Phase 5)
CSV: ONE documented format (ADR 0003; no per-institution profiles), with preview, invalid-row and duplicate detection, correct/exclude rows, proposed conversions, explicit confirmation before commit, import history (see docs/imports.md). PDF (Phase 14, ADR 0014): text PDFs only (pypdf, no OCR), Australian dividend/distribution advices in AUD; only payment date, payer (ASX code), dividend paid (gross) and tax withheld are read (franking details ignored), each with its page and source line, shown in the same review/edit/exclude/duplicate/atomic-commit staging as CSV; an unrecognised or inconsistent statement is refused with a reason and stages nothing. Revolut Flexible Cash Funds monthly statements are read too (`interest_statements.py`: gross = total earned return, expenses = total fees, daily lines must add up). Phase 15 (ADR 0015): readers are an ordered registry in `statement_readers.py` (exactly one may claim a file; two claims refuse the file naming both), a statement yields zero, one or many rows (`StatementResult`: rows, notices, fingerprint); "nothing to import" and "recognised, not imported" are summary lines, not errors, and an upload with nothing to import creates no batch; two files with the same reader and fingerprint are one statement; displayed file names mask digit runs of six or more; `tools/pdf_inventory.py <folder> [--recursive]` reports what a folder contains without amounts or names. HSBC UK savings statements (Phase 16, ADR 0016; `hsbc_savings.py`, layout mode): one Interest payment (GBP, monthly) per "GROSS INTEREST" credit, payment date = credit date, income period end = the TO date, every balance must reconcile or the statement is refused, transfers are not staged, unknown row types refuse; continuity between statements is a warning only. RVB current-account statements (Phase 17, ADR 0017; `rvb_account.py`, layout mode): one quarterly Interest payment (EUR) per interest closing (gross = HABENZINSEN lines, withholding = the booked Kapitalertragsteuer + Solidaritätszuschlag + Kirchensteuer with each named and its base in the comment, payment date = booking date), every other statement is nothing to import (prize credits are a notice) and every statement's balance must close or it is refused; unknown booking texts (fees) refuse the statement. E*TRADE client statements (Phase 18, ADR 0018; `etrade_client.py`, layout mode): one Dividends payment (USD) per income event, a `Dividend` (fund, monthly) or `Qualified Dividend` (company stock, quarterly) line paired with its `Tax Withholding` line, organisation = the tidied printed name, "via E*TRADE" in the comment; the cash-flow total, the sweep table, the income summary by class and the tax-withholding total must all reconcile or the statement is refused; the messages section is never read. Fidelity Stock Plan reports (Phase 19, ADR 0019; `fidelity_stock_plan.py`, layout mode): one Dividends payment (USD) per "Dividend Received" line; the withholding of an event is the SUM of all its tax postings (original, reversal, re-booking) across the statements of the upload (`settle`, a hook of the reader registry), with batch warnings for postings of events outside the upload, rows of the latest statement marked "may be revised by a later statement", and income/tax totals reconciled (tax by absolute value); stock deliveries, sales and journals are notices only. Managing-agent rental statements (Phase 21, ADR 0021; `hodges_rental.py`): one Rental row (AUD, monthly) per statement, gross = rent received, expenses = the listed costs and sundry fees (council and water rates included), payment date = statement date, income period from the paid-to dates; the owner withdrawal is a notice only; organisation = the setting `DJANGO_RENTAL_ORGANISATION` (never in code). MECU account statements (Phase 22, ADR 0022; `mecu_account.py`, layout mode; pypdf alone cannot open them, `pdf_text.repair_xref_counts` fixes the one-entry xref defect in memory): one Interest row (AUD, monthly) per Interest Credit, Bonus Interest and term-deposit interest, gross/withholding from the memo lines (gross - withholding = credit or refuse), the receiving credit of a term-deposit payment is a transfer, every balance must be proved, dates get their year from the statement date, the annual Payment Summary is a warning-only cross-check. Ord Minnett Cash Management Trust statements (Phase 23, ADR 0023; `ordminnett_cmt.py`, layout mode): the interest rows are made by the reader's batch step (`settle`): exact repeats across overlapping monthly/financial-year statements are staged once and listed, each overseas-withholding debit is paired with the interest credit of the same calendar quarter, direction comes only from the running balance; dividend and other credits are not staged, scheme consideration, stock-sale proceeds and large credits are date-only notices, sales are never imported; the staging classifies files after the batch step. Phase 24 (ADR 0024) closed the Australian statements: `tools/collision_report.py` (read-only, counts only) reports how the staged rows relate to the payments already in the database; nothing existing is ever modified or deleted. Phase 25 (ADR 0025): the joint current account (same bank and layout as RVB) has its own reader `rvb_joint` (`rvb_joint.py`, layout mode), claimed only when the printed account number equals the setting `DJANGO_JOINT_RENTAL_ACCOUNT` (digits only, never logged or shown unmasked; `rvb_account` steps aside for that account only); only grammar and arithmetic refuse a statement (bookings parse, page carries agree, balance closes), unmatched lines are normal; what counts as rent is `StatementRule` data edited in the admin (never names in code; normalised matching; conflicts are never staged; `tools/rule_preview.py` previews without names or amounts); Phase 26 (ADR 0026): one row per credit matched by a `tenant_rent` rule (EUR, monthly, whole credit, category from `DJANGO_JOINT_RENTAL_CATEGORY` default `Rental (joint)`, never created by the importer, organisation = the rule's, created with country DE) and per `service_charge_settlement` credit; a credit with a Kaution is split only when the labelled Kaution and Miete figures sum to the credit (deposit = notice), else left out with a notice; a "Miete" credit no rule matches is a notice; all debits and other bookings are ignored and counted; rental costs are deferred by the owner. Phase 27 (ADR 0027): `tools/collision_report.py` also reports (counts only, read only) how the staged joint-rent rows relate to the payments already in the database; nothing existing is modified or deleted. `cryptography` is a pinned dependency (opens AES-encrypted bank PDFs). Phase 28 (ADR 0029): stored originals under `UPLOAD_DIR/imports/` outlive a deleted year unless the owner ticks the (off by default) box on the year-delete confirmation page, which removes the stored files and import history of the batches used by that year only; the imports page offers per-batch "Delete stored file" (history and rows kept, "original removed") and "Delete batch completely" (never any payment), and `manage.py stored_files_report [--apply]` lists and removes unreferenced files (dry run by default). Removal happens only through these confirmed POST actions, never on the app's own initiative, so "keep originals" in the financial principles means the app keeps them until the owner deliberately removes them; backups are not touched. Extraction (`core/services/pdf_text.py`, `dividend_statements.py`, `interest_statements.py`) is separate from the core model. Never send documents to an external AI/OCR service unless I explicitly enable it and understand the data sharing.

## Security and privacy
- No personal or identifying data in tracked files. Use git-ignored `local/secrets/`, `local/samples/`, `local/uploads/`, `local/exports/`, with tracked placeholder/README files only. Synthetic sample CSV/PDF for tests only.
- `.gitignore` excludes: virtualenvs, SQLite files, .env files, secrets, uploads, exports/reports, private fixtures, temp files, OCR output. It is not a security boundary: review staged files before every commit.
- Django auth required for all financial views (single user via `createsuperuser`; no hard-coded identity). CSRF, form validation and password hashing via Django defaults. No public static URLs for uploads/reports: static files are the app's own stylesheet only (WhiteNoise, Phase 9); uploads and exports are never served as static files. Never log payment details, secrets or document contents. SECRET_KEY and DB settings come from environment variables.

## Environment and deployment
- Pin Python and Django versions (verify compatibility first; prefer a current Django LTS) and use a lock file. Runs locally with no Podman or DB server.
- SQLite with a dedicated, env-configurable DB path (default under `local/`, production e.g. `/var/lib/tax-healthcare-tool/db.sqlite3`). Never repo-relative in production. Never touch the existing server app's database.
- Deployment (built in Phase 8; the repository's deployment is rootless Podman + Quadlet run by the service user `homeapps` (Phase 9A, ADR 0007; served through the gateway over https, URL prefix `/tax-healthcare`; Phase 9B, ADR 0008: the unit also joins the gateway's Podman network `gateway`, `DJANGO_BEHIND_TLS_PROXY=1`, https origin trusted, Secure cookies (`use_https: true` from G3) and HSTS 0; Phase G3, ADR 0009: the published port is loopback-only and the plain-HTTP origin is removed; no Caddy configuration in this repo); routine deploys need NO sudo (`make deploy` etc.) and only `make bootstrap-rootless` and `make migrate-copy` may use it. Until the owner runs the cut-over, the server still runs the Phase 8 rootful container; see docs/podman-explained.md. Explain Podman terms plainly: the owner is new to it): own image, container name, env, data dir, DB, port/route, health check, WSGI server (not runserver), separate dev/prod settings, backup and tested restore, rollback plan. Inspect the existing Ansible conventions first, propose the smallest change, and ask before modifying shared infrastructure.
